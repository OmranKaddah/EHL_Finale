## My request:
Design and implement a multi-agent RFQ system with four autonomous, domain-specialized browser agents and one browserless central orchestrator. Each specialist owns one of Atira's four provided CDP browsers. Use dependency-aware asynchronous execution, structured evidence exchange, deterministic pricing and validation, comprehensive per-agent tracing, and a four-browser live debugging view.&#x20;

The system must remain genuinely model-directed, generalize to the unseen private scenario, survive individual agent failures and complete a signed bid under the 20-minute limit. Benchmark this architecture against a simpler sequential baseline. If concurrency introduces more failures than benefits, prioritize reliable completion over agent count.

That is five logical agents, but only four browsers. The orchestrator doesn't need its own browser, so it respects Atira's maximum of four.



But there's a catch: the four agents aren't entirely independent.

For example, the ERP agent cannot confidently select a hydraulic cylinder until the specification agent has identified the exact technical requirements. Similarly, the email agent cannot safely select an approval without knowing the correct tender reference.

So I would implement dependency-aware parallelism, rather than four agents blindly working at the same time.

## How execution should proceed

Phase 1 — Parallel discovery

All four agents navigate their assigned websites. The tender agent identifies the tender, the specification agent investigates available documents, the ERP agent learns how to search materials, and the email agent locates relevant correspondence.

No agent assumes that a particular record is correct before verifying it.

Phase 2 — Exchange structured findings

Once the tender and technical requirements are resolved, the orchestrator provides the actual requirements to ERP and the tender reference to email.

Each agent publishes structured evidence with its source, revision, timestamp and confidence.

Phase 3 — Calculate and validate

A deterministic Python engine calculates the bid. The orchestrator checks for missing evidence, inconsistent quantities, incorrect discounts and unresolved material matches.

If something doesn't agree, it sends a targeted follow-up task to the appropriate specialist.

Phase 4 — Submit

The tender agent enters the bid, the email agent obtains the signing TAN when needed, and the system verifies that the portal actually accepted the submission.

## Three things I'd be careful about

1\. Don't make four agents compete over the same browser. Assign exactly one Atira-provided browser to each specialist. They can use tabs or frames within that browser.

2\. Don't let agents exchange huge raw histories. Give them typed messages and a shared evidence store. Otherwise, multi-agent communication consumes time and tokens without adding much value.

3\. Avoid unnecessary LLM calls. Qwen allows up to 32 concurrent requests per team, but latency and simulated cost still matter. One specialist making 50 unproductive calls is worse than a well-designed agent making 10.

And I'd add one resilience mechanism: a deadline-aware orchestrator. With a few minutes left, it should stop optional exploration and prioritize validating and submitting whatever complete bid positions are available, rather than timing out with zero.
